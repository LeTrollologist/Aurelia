# Aurelia v3.7.0 — viewport fidelity and stabilization

This release closes the viewport-fidelity phase and the stabilization items behind it. One
investigation ended in a documented rejection rather than a feature: the viewport keeps its GDI
8-bit presentation path, and the reasoning is now recorded instead of implied.

## Viewport

### DPI transitions preserve the framed canvas (#46)

`zoom` and `pan` are physical pixels, so a per-monitor DPI change used to make the document
appear to shrink while the view jumped. Both now scale with the window ratio alongside the panel
metrics, which keeps the visible canvas fraction identical across 100% / 125% / 150% / 200%
transitions. The same `AppState::apply_dpi_scale` also handles the no-op and inverse cases, so
moving back and forth does not accumulate drift. Window geometry is still owned by Windows
(`WM_DPICHANGED`'s suggested rect); Aurelia stores no geometry of its own to restore.

### Navigator DPI and dock sizing (#45)

The Navigator texture is no longer a fixed 320 px image. Its target width follows the dock's
physical width (`0.92 × dock`, clamped to 160–720 px), so a 200% monitor rebuilds at roughly
twice the resolution instead of upscaling, and resizing the dock updates the preview. A DPI or
dock-size change invalidates the texture through the existing revision gate, so idle frames still
do no work. Framing, letterboxing and panel layout are unchanged and remain covered by their
tests.

### RGBA16 presentation investigated and rejected (#44)

A native RGBA16 presentation path was evaluated against the constraint of keeping the GDI
framebuffer and the existing UI:

- GDI has no 16-bits-per-channel DIB blit; Direct2D's bitmap path ends at 8-bit UNORM for this
  use; a real 16-bit path means a D3D11 texture and DXGI swapchain, i.e. a renderer rewrite.
- Dithering the 16→8 conversion trades banding for visible noise and cannot add precision beyond
  the panel; it was rejected on fidelity grounds.
- The display conversion is already rounded (`(v + 128) / 257`), so it adds no bias, and
  `composite_layers_srgb16` remains available to export and future presentation work.

Decision and evidence: [docs/RGBA16_PRESENTATION.md](../docs/RGBA16_PRESENTATION.md).

## Rendering

### Bilinear transparent edges corrected (#47)

Bilinear sampling averaged colour and coverage independently, so a transparent black neighbour
darkened a soft edge and a transparent coloured neighbour tinted it. Both samplers now interpolate
**premultiplied** colour, then unpremultiply by the exact coverage before quantising. A
neighbourhood whose four samples share one alpha value takes the original arithmetic, so fully
opaque and uniformly semi-transparent output is byte-identical to before; only mixed-alpha edges
change. The four 8-bit transform baseline digests for bilinear were updated deliberately;
bicubic is untouched and its digest did not move. Fixtures cover 8-bit and 16-bit, transparent
black, transparent colour and the uniform-alpha fast path.

## Performance and stability

### Sparse 16-bit throughput (#48)

Gate 2 measured **0.75** against the 0.60 budget on the reference machine (u8 126.6 MPix/s,
Srgb16 92.4 MPix/s, spread 0.64 .. 1.08). The budget remains the gate; 0.75 is recorded as an
exploratory target, not enforced. `bench_composite` gained `--filter <text>` so a single case can
be measured in isolation for paired A/B runs.

### Luminosity profiling (#49)

Luminosity remains the slowest general-path mode: 68.3 MPix/s in the full interleaved pass
(Normal 76.7), 92.2 MPix/s when measured alone. Inspection attributes the gap to the W3C
SetLum + ClipColor sequence rather than an implementation accident, and no optimization was
accepted without a paired, correctness-neutral win. The measured values are the rollback
reference in PERFORMANCE.md.

### Long-session soak (#50)

`crates/aurelia-io/tests/soak.rs` runs an explicit, repeatable 120-cycle session over a 192×192
RGBA16 document: paint, Gaussian blur, transform patch, three undos + three redos, save/load every
15 cycles, animation-frame add/sample/delete every 10. With an 8 MiB history budget it recorded
36 retained steps at 8.36 MB, 30 KB of live-heap growth after warm-up (allowance 4.5 MB) and no
state inconsistency. The command and the record are in PERFORMANCE.md.

### Undo/redo under eviction (#51)

New tests exercise eviction with 16-bit pixel deltas and mask commands, verify that undoing and
redoing everything that survived restores the exact final bytes, that redo is invalidated and its
memory released after a new edit, and that a document saved after eviction reloads identically
(including 16-bit storage and mask bytes).

## Compatibility

- AUR v1/v2 load read-only; saves continue to write v3.
- Document formats are unchanged. No colour conversion was added or removed.
- The 8-bit viewport presentation remains, now documented as a decision.
- Mixed-alpha bilinear output changes by design; the corrected fixtures and four updated 8-bit
  digests are the record.
